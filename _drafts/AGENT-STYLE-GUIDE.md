## Структура статьи (строго)
1. **Лид**: 2–4 предложения, сразу ответ на вопрос, обращение на «ты», живой тон. БЕЗ «Сразу к делу:».
2. **H2-вопросы**: 4–7 разделов. Заголовки — вопросы («Как …?», «Почему …?», «Что делать, если …?»).
3. **Частые вопросы**: `## Частые вопросы`, внутри H3-вопросы с ответами (3–5 шт).
4. **Полезные ресурсы**: `## Полезные ресурсы`, список из 2–4 ссылок (ArchWiki + нужные).
5. **Заключение**: `## Заключение`, 2–4 предложения итога.

## Режимы написания партий (рекомендую ПОСЛЕДОВАТЕЛЬНЫЙ)

**Режим A — последовательный (основной, самый дешёвый):**
- Агенты запускаются ПО ОДНОМУ, каждый следующий — через `task(task_id="ses_...")` продолжение ТОЙ ЖЕ сессии (не новый вызов).
- Контекст гайда и эталонов читается ОДИН раз на всю партию (первый агент прочитал — остальные наследуют).
- Один вызов = одна статья. После каждого — ждать результат, затем запускать следующую.
- Промпт следующего агента: «Продолжи. Напиши статью N+1: тема, слаг, дата, ссылки партии» (~40 слов, без повторения гайда).
- Итоговая экономия против 4 параллельных: **~60–70%** (общий контекст гайда/эталонов оплачивается 1 раз, а не 4).

Пример цепочки:
1. `task(category="deep", session A, prompt="прочитай гайд, напиши статью 1")`
2. `task(task_id="ses_A", prompt="продолжи, напиши статью 2")`
3. `task(task_id="ses_A", prompt="продолжи, напиши статью 3")` — и т.д.

**Режим B — параллельный (резерв, когда важна скорость):**
- 4 агента сразу, каждый с коротким ТЗ + «прочитай гайд».
- Допустимо при дедлайне, но стоит на ~2x дороже и выше риск сбоя.
- Партии 2.11–2.14 писались этим способом с ДЛИННЫМИ промптами — из-за этого токены улетали впустую (см. историю).

**Вывод:** по умолчанию — Режим A (последовательно, 1 сессия на партию). Параллель — только по явной команде.
